# COIN-LIO → Super-LIO source and semantics map

## Scope and source identity

This is a read-only source audit for P2. It does not copy or alter production code and did not run a bag. The official checkout was verified at branch `main`, commit `76729cc4feb3649cbd79d28f82d9f62a2c82889b`, with an empty `git status`. The workspace baseline during this audit was `p2-faithful-coin-on-super`, commit `cc67e6b8e7a81f7f033e376dc74e0f1586fe87a2`.

The existing P1 photo path is the independent CUBE/IGM implementation; its existence does not demonstrate COIN parity. P2.1 now compares the initial `CoinOusterProjector` and `CoinImageProcessor` against the pinned official frontend on ten TunnelD scans. The image-construction gate passes exact equality for raw/filtered intensity, derivatives, range, ownership, masks, u8 output, and projected-index maps; sampled projected UV differs by at most `1.42e-14` pixels. The input is the same official-preprocessed corrected cloud and identity distortion transforms, so this result covers current-frame semantics only. `CoinFeatureManager`, COIN residual linearizer, and COIN fusion path remain unimplemented; their parity is not claimed.

## Exact COIN observation semantics

### Ouster frame and projection

The ENWIDE input is not an arbitrary point cloud that can be projected with `atan2` alone. COIN reads the 128 calibrated beam elevations, 1024 columns, per-row pixel-shift table, beam-origin offset 27.67 mm, and ENWIDE Ouster point fields from `os_enwide.json` and the launch. It converts the calibrated angles from degrees, applies the beam-offset spherical model, and interpolates vertical pixel location between the actual beam angles (`refs/COIN-LIO/src/projector.cpp:17-32,52-96,161-210`). `image/destagger` defaults to true in the projector; `u_shift` is explicitly zero for ENWIDE (`launch/mapping_enwide.launch:11`, `src/projector.cpp:87-96`).

The dense intensity/range image is organized using the Ouster metadata lookup, not the projected corrected-cloud UV. `Preprocess::ouster_handler()` retains original organized point index and original range (`refs/COIN-LIO/src/preprocess.cpp:17-52`). `Projector::indexFromPixel()` applies the row's pixel shift and optional destagger (`src/projector.cpp:155-159`); `createImages()` uses that mapping for dense pixels, while separately creating the rounded end-frame projection lookup (`:103-153`). The range image is the saved raw range, not the norm of the deskewed pixel owner.

For a feature, the official path first expresses its fixed global point in the predicted scan-end LiDAR frame. It looks up the closest corrected point associated with that projected bucket, selects that point's acquisition-time inverse transform, transforms the feature into that historical LiDAR frame, and projects again into the image that still represents the original scan (`projector.cpp:213-281`). Thus, “the scan was deskewed” is not by itself equivalent: COIN returns a feature to the acquisition-time image geometry before reading intensity/range.

### Image values, masks, and feature patch

The estimator works with the processed float image. With ENWIDE defaults it starts from Ouster `intensity`, multiplies by 0.25, subtracts the separable FIR line estimate and clips negatives to zero, normalizes local brightness by a 41×7 box-filtered image plus one, applies 3×3 Gaussian blur, and truncates above 255. Float central differences form `img_dx`/`img_dy`; the 8-bit image is a display output (`refs/COIN-LIO/src/image_processing.cpp:68-141`). The mask combines the two configured connector rectangles, raw range `[0.7,30]` m, and a 7×7 erosion; an additional 10-pixel border and radius-10 feature suppression mask are applied by the feature manager (`image_processing.cpp:143-167`; `feature_manager.cpp:12-27,34-55,483-491`).

A selected center creates exactly 25 paired samples: integer patch UVs, 3D corrected points transformed into global coordinates using the post-update `T_GL`, and float intensities from the processed image (`refs/COIN-LIO/src/feature_manager.cpp:91-116`). Those 25 world points and 25 intensities are the fixed reference patch. Each frame updates the current UVs and center after successful tracking; it does not re-anchor the 3D points or refresh the reference intensity. NCC is checked after patch-wide projection, mask, range, and occlusion gates (`feature_manager.cpp:372-471`). A failed point invalidates the entire patch. A surviving patch is removed once its lifetime reaches the configured maximum; detection then replenishes the pool.

### Complementary geometry weak score

COIN's score is specifically a feature proposal/ranking rule. The input weak directions are extracted from the final geometric translation Jacobian, not from the fused photo+geometry matrix and not from the smallest eigenvalues of a six-dimensional CUBE Hessian. `h_geo_last` stores the first three columns of the final geometry measurement Jacobian (`refs/COIN-LIO/src/laserMapping.cpp:831-835`). For each translation Jacobian row, COIN normalizes it and contributes `abs(row·v)` to an eigenvector's score only when the dot magnitude exceeds 0.5. Eigenvectors are ordered by ascending eigenvalue from `SelfAdjointEigenSolver`; score below `n_uninformative` (default 25) marks that vector weak (`laserMapping.cpp:329-353,1198-1209`). It rotates those global translation directions into the current LiDAR frame, then falls back to LiDAR XYZ if no weak directions exist (`:1212-1229`).

For a candidate image patch, COIN obtains a local dominant image derivative from `cornerEigenValsAndVecs`. For each weak direction `v`, it computes and normalizes `du/dp · v`, then scores the absolute image derivative along that 2D motion. Descending per-direction lists are traversed round-robin and candidate IDs are deduplicated (`refs/COIN-LIO/src/feature_manager.cpp:176-227,232-268`). The initial gradient threshold/NMS proposes spatially separated candidates; the complementary score then selects candidates that respond to distinct weak translation directions. The direction normalization means this score uses image response along a direction, not the magnitude of how far the point projects under that direction.

### Residual, correction Jacobian, tangent order, and fusion

At a valid patch pixel, official residual is

```text
r = I_current(u,v) - I_reference
```

with bilinear float sampling (`refs/COIN-LIO/src/laserMapping.cpp:745-776`; `include/common_lib.h:285-303`). The image derivative is computed by central sampling at ±1 pixel (`laserMapping.cpp:745-755`). The position-projection chain uses the acquisition-time LiDAR transform, the fixed `T_IL` extrinsic, and the calibrated Ouster `du/dp` (`laserMapping.cpp:760-767`).

COIN's `h_x` is the **correction-direction Jacobian**, i.e. the negative residual derivative. This sign follows from the source, not from the variable name: for `p_I=R_IG(p_G-t_G)`, the negative derivative under an additive global translation and a right-local SO(3) increment is `[R_IG, -hat(p_I)]`; COIN left-multiplies this by `R_Li_I` and by image derivatives (`laserMapping.cpp:760-776`). The filter uses `K_h = K * dyn_share.h` and applies `x.boxplus(dx)` (`refs/COIN-LIO/include/IKFoM_toolkit/esekfom/esekfom.hpp:1738-1740,1814-1817`), so direct normal-equation accumulation uses `b = H_correctionᵀ r`, not `-H_correctionᵀ r`.

COIN's pose tangent ordering is `[δp_global(3), δθ_right(3)]` in the first six state DOFs: the state manifold declares `pos` before `rot` (`refs/COIN-LIO/include/use_ikfom.h:12-21`), SO(3) boxplus is right multiplication `R ← R·Exp(δθ)` (`include/IKFoM_toolkit/mtk/types/SOn.hpp:231-239`), and the official Super-LIO-derived `StatesGroup` implements that same right multiplication with translation after rotation in its 18-vector (`include/common_lib.h:108-143`). Super-LIO's six-dimensional pose normal-equation order is instead `[δθ_right_body(3), δp_global(3)]`: `ESKF::Update()` applies `R ← R·Exp(dx[0:3])`, then `p ← p+dx[3:6]` (`src/super_lio/src/lio/ESKF.cpp:118-124`). The tangent must therefore be reordered and frame-labelled explicitly before adding a COIN row to Super-LIO. Verify any IMU/body/LiDAR rotation mapping with finite differences; do not copy the six columns positionally.

At the official fusion boundary, `λ=0.00095` scales both the COIN `h_x` and `h` rows, while geometry rows remain as built; all rows share scalar measurement variance argument `R=geo_std=0.001` (`refs/COIN-LIO/src/laserMapping.cpp:803-840,950-955,1195`). Therefore, before any Super-specific weight conversion, the COIN photo normal-equation contribution is

```text
A_photo = (λ²/R) Σ H_correctionᵀ H_correction
b_photo = (λ²/R) Σ H_correctionᵀ r
```

The local Super estimator receives already accumulated `HTVH`/`HTVr` rather than raw rows, and its geometry terms are preweighted in `SuperLIO::Observe()` (`src/super_lio/src/lio/super_lio.cpp:454-512`). The conversion between COIN's scalar `R` domain and Super's existing geometry normal-equation units must be written down before integration. `λ` belongs only to the raw COIN intensity residual domain; it cannot be reused for P1 CUBE/IGM values.

## Implementation and parity guidance

1. Keep P1 CUBE code behind its own `cube_p1` path, add `coin_faithful` as a separate frontend, and leave `off` byte-identical. The current P1 `CubeProjector`, IDW/IGM, scalar landmarks, gates, and CUBE residual helper should not be repurposed as COIN equivalents.
2. Reproduce and compare Ouster image ownership, range, masks, float values, derivatives, and projected UVs before feature work. Keep metadata and point-index ownership as explicit frame data. Audit collision/duplicate ordering in the official lookup against deterministic output.
3. Implement and shadow-check feature candidates, score, 5×5 fixed references, acquisition-time projection, NCC/gates, lifetime, and replenishment before estimator fusion. Match feature IDs deterministically and compare per-frame add/remove/reject counts.
4. For a fixed feature/pose, test projector `du/dp`, bilinear image gradient, and complete 25-pixel correction Jacobian against finite differences. Compare COIN `H_correction` to `-∂r/∂δ` in COIN's `[position, right-local rotation]` order; then test the explicit Super reorder/frame transform in `[right-local rotation, position]` order. Include real TunnelD points and samples away from interpolation/clamp discontinuities.
5. Before connecting to `ESKF::UpdateObserve`, express both `A` and `b` in Super's six-dimensional pose order and confirm the P2 mode adds only a measurement channel. Record how official scalar `R` and `λ²` translate to Super's already weighted `HTVH`/`HTVr`; do not tune that conversion against ATE.
